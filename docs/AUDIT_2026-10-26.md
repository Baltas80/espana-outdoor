# Auditoría técnica de España Outdoor — 2026-10-26

## Alcance y límites

Auditoría estática del árbol de `feature/profile-registration-20261024`, con revisión de código Flutter/Dart, pruebas, migraciones SQL, servicios Go y workflows de GitHub Actions. No se tuvo acceso a ejecución local Flutter/Android, credenciales de staging, base de datos real ni dispositivo físico durante esta revisión. Por tanto, los estados siguientes describen evidencia de código y pruebas existentes, no una certificación de funcionamiento en producción.

## Diagnóstico ejecutivo

La aplicación contiene implementaciones reales para MapLibre, routing Valhalla, grabación y persistencia de tracks, regreso sobre el recorrido, catálogo/descarga offline y Rescue Link. El riesgo principal está en validar los flujos completos, en especial Android real, servicios configurados y comportamiento ante fallos. Varias páginas de rutas son contenido editorial y no equivalen a un catálogo de rutas con geometría verificada.

Se detectó documentación contradictoria: `docs/PROJECT_STATUS.md` todavía describe Agus Maps/CoMaps como renderer Android, mientras `pubspec.yaml`, `lib/features/map/maplibre_map_page.dart` y `docs/architecture/ADR-0001-maps-and-offline.md` usan MapLibre. La documentación de estado debe corregirse para que no induzca cambios de arquitectura erróneos. El README también contiene afirmaciones cartográficas que deben reconciliarse con la implementación actual.

## Hallazgos concretos

1. **Documentación cartográfica desactualizada.** `docs/PROJECT_STATUS.md` señala Agus Maps/CoMaps y PMTiles fuera del renderer, pero el código actual utiliza MapLibre. Debe actualizarse según el código actual y las ADR vigentes.
2. **Rutas de descubrimiento no son rutas verificadas.** Las tarjetas en `lib/features/routes/routes_page.dart` contienen datos editoriales y al pulsarlas abren el planificador; no se debe presentar esa interacción como una ruta precalculada.
3. **Routing necesita endpoint real.** `ValhallaRoutingService` tiene pruebas de parsing con clientes simulados; esto no prueba disponibilidad, perfiles de costing, conectividad ni routing de producción.
4. **Grabación GPS tiene persistencia de recuperación.** `RouteRecordingStore` segmenta tracks y tiene pruebas de persistencia/recuperación. No demuestra supervivencia a restricciones de batería, cierre forzado o comportamiento OEM.
5. **Rescue Link tiene controles de seguridad en el backend.** El servicio autentica OIDC, cifra ubicación, almacena hashes de tokens y comprueba expiración/revocación en endpoints. Las pruebas inspeccionadas incluyen criptografía y precisión por rol, pero no constituyen una prueba de integración contra una base de datos y un issuer reales.
6. **Compartición de ubicación en tiempo real no está demostrada.** Los endpoints inspeccionados permiten crear el enlace, aceptarlo, revocarlo y consultar la ubicación guardada. No se encontró en el router inspeccionado un endpoint explícito para actualizar continuamente la ubicación del propietario; confirmar si existe otro mecanismo antes de afirmar que el seguimiento se actualiza durante el incidente.
7. **CI específico no equivale a QA del producto.** `.github/workflows/profile-integration.yml` ejecuta pruebas Go, análisis Flutter y comprobaciones de módulos web dentro de su alcance de paths. Se necesita una ruta de CI que valide los flujos Android críticos y evidencia de un smoke test en dispositivo.

## Prioridades de implementación

### P0 — seguridad y estabilidad

1. Ejecutar el workflow de integración relevante y registrar el resultado real de análisis/tests; no fusionar basándose solo en una vista previa web.
2. Ejecutar build Android staging y smoke test de mapa/GPS en dispositivo, conservando logcat y resultado de la prueba.
3. Auditar Rescue Link end-to-end: creación, token compartido, autenticación del respondedor, autorización por rol, lectura, expiración, revocación y acceso tras revocación. Confirmar qué significa “ubicación actualizada” y si el backend la recibe después de crear el enlace.
4. Verificar que el usuario ve claramente el estado sin cobertura/GPS y que Rescue Link no se presenta como sustituto de emergencias oficiales.

### P1 — rutas y navegación

5. Probar Valhalla real con endpoint configurado y respuestas de error/timeout.
6. Completar el flujo de grabación en Android: iniciar, pausar, reanudar, detener, recuperar tras interrupción, historial y exportación GPX.
7. Validar regreso sobre el track y comunicar explícitamente que sigue el recorrido grabado, no una ruta recalculada por caminos.
8. Validar catálogo/descarga offline, integridad, apertura de MapLibre sin red y recuperación tras descarga interrumpida.
9. Sustituir progresivamente las tarjetas editoriales por catálogo de rutas con geometría y procedencia verificadas.

### P2 — experiencia y sincronización

10. Verificar sincronización de perfiles entre web y Android, sin ampliar cosmética ni logros.
11. Mejorar estados, errores y estadísticas cuando los datos y servicios reales ya estén validados.

## Criterio de cierre

No declarar una función “operativa” solo porque el código exista, pase análisis estático o despliegue una página web. Para las funciones P0/P1 se requiere evidencia del servicio configurado y pruebas de uso/errores; para Android, build, instalación y prueba real en dispositivo. No se cambian servicios de producción ni se introducen motores cartográficos alternativos durante esta auditoría.
