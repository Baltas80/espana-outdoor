# Live Data Gateway

First-party gateway for official live data. Provider credentials stay on the server; mobile clients receive normalized records with explicit provenance and freshness.

## Current provider

- AEMET OpenData municipality daily forecasts (`aemet-weather`).
- AEMET API key is read only from `AEMET_API_KEY` at runtime.
- `AEMET_API_KEY_EXPIRES_AT` is mandatory and is checked at startup.
- The gateway uses OIDC bearer authentication, client-scoped role authorization for source data, and per-subject rate limiting.
- AEMET failures use bounded retry/backoff and stale-cache fallback.
- The same service exposes a canonical community profile API when a TLS-protected PostgreSQL DATABASE_URL is configured.

## OIDC authorization policy

The gateway has two distinct OIDC controls:

1. `OIDC_AUDIENCE` is the resource-server/API audience that must be present in every accepted access token. It is separate from the public web/mobile client ID.
2. `OIDC_REQUIRED_ROLE` is the exact application permission required by protected gateway endpoints.

For authorization, the required role is accepted **only** from:

`resource_access[OIDC_AUDIENCE].roles`

The following are never treated as equivalent client authorization:

- `realm_access.roles`;
- roles under another `resource_access[client_id]`;
- the same role name under a different client.

Missing or malformed authorization claims fail closed with HTTP 403. Authorization is enforced by the backend after cryptographic OIDC validation; the Flutter client is not trusted to enforce permissions.

## Runtime configuration

| Variable | Required | Purpose |
|---|---:|---|
| `OIDC_ISSUER` | yes | OIDC issuer used to validate product access tokens |
| `OIDC_AUDIENCE` | yes | Resource-server/API audience and key for roles under `resource_access[OIDC_AUDIENCE]` |
| `OIDC_REQUIRED_ROLE` | yes | Exact role required under `resource_access[OIDC_AUDIENCE].roles` |
| `AEMET_API_KEY` | yes | AEMET provider credential, runtime only |
| `AEMET_API_KEY_EXPIRES_AT` | yes | RFC3339 expiry used for startup/health monitoring |
| `DATABASE_URL` | for profiles | PostgreSQL URL; production must use sslmode=require or stronger |
| `ALLOW_HTTP_DEV` | no | Defaults to false; true permits HTTP only to the internal `keycloak` service and `sslmode=disable` only for loopback or the internal `postgres` service during local development |
| `PROFILE_MIGRATION_PATH` | no | Defaults to migrations/001_community_profiles.sql |
| `COMMUNITY_ALLOWED_ORIGINS` | no | Comma-separated HTTPS origins; defaults to the production website domains |
| `AEMET_BASE_URL` | no | Defaults to `https://opendata.aemet.es/opendata/api` |
| `PORT` | no | Defaults to `8080` |
| `CACHE_FRESH_TTL` | no | Defaults to `10m` |
| `CACHE_AGING_TTL` | no | Defaults to `10m` |
| `CACHE_STALE_TTL` | no | Defaults to `40m` |
| `RATE_LIMIT_RPS` | no | Defaults to `2` |
| `RATE_LIMIT_BURST` | no | Defaults to `10` |

## API

- `GET /healthz` — gateway process health plus AEMET key-expiry state.
- `GET /v1/sources/aemet-weather/health` — normalized provider health/freshness.
- `GET /v1/sources/aemet-weather?municipalityCode=03099` — normalized forecast envelope.
- `GET /v1/me` — provisions/returns the authenticated user's canonical profile.
- `PATCH /v1/me` — updates only the authenticated user's display name.

The community profile endpoints require a cryptographically verified Keycloak access token with the configured resource-server audience and the JWT payload claim `typ=Bearer`. `DATABASE_URL` must be configured to enable the profile API; the local Compose example wires the PostgreSQL service and applies the migration at startup. ID tokens (`typ=ID`), refresh tokens, and tokens without an explicit bearer type are rejected even if they share the issuer, signing key, or frontend-client audience. Configure an audience mapper for this API and set `OIDC_AUDIENCE` to that API audience; do not rely only on the public web/mobile client ID. The service derives the subject from the verified token and never accepts a user ID from the request. Email is imported only when the issuer sets email_verified=true. PostgreSQL generates the canonical profile UUID.

The source-data endpoints continue to require the configured client-scoped role.

Example profile response (the ID is generated by the server):

```json
{
  "id": "server-generated-uuid",
  "displayName": "Outdoor User",
  "email": "verified@example.test",
  "createdAt": "2026-11-14T10:00:00Z"
}
```

Update only the display name with `PATCH /v1/me` and a JSON body containing `displayName`. Unknown fields (including `subject`, `id` and `email`) are rejected. Profile endpoints return HTTP 503 when DATABASE_URL is not configured; existing AEMET endpoints remain available.

CORS is restricted to COMMUNITY_ALLOWED_ORIGINS, allows bearer authorization headers and GET/PATCH only, and does not enable credentialed cookies or wildcard origins.

The client must never send the AEMET API key. The gateway attaches it only to the AEMET provider request.

## Freshness semantics

`current` means the gateway cache is within `CACHE_FRESH_TTL`.

`aging` means the fresh window has elapsed but the cached response is still within the next `CACHE_AGING_TTL`.

`stale` means a cached response is older than the aging window but still inside `CACHE_STALE_TTL`; it is returned only when a provider refresh fails.

`unavailable` means there is no usable cached response.

## Deployment

Use HTTPS at the edge, inject secrets through the platform secret manager, and expose `/healthz` to the infrastructure monitor. Do not publish AEMET credentials, access tokens or exact emergency locations in logs.


## Shared identity setup

Configure the web and Android clients against the same trusted OIDC issuer and public client using Authorization Code + PKCE (S256). Register both the HTTPS web callback and Android redirect URI in the client's allowlist. Configure an access-token audience mapper so the access token includes OIDC_AUDIENCE. Never add a client secret to Flutter or static web assets.

The first authenticated GET /v1/me provisions a profile row from the verified token subject. The subject remains internal; clients receive only the server-generated profile UUID. PATCH /v1/me accepts exactly displayName, preventing callers from selecting another account or changing their email.
